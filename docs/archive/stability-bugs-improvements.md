# מסמך אפיון — יציבות, באגים ושיפורים

**פרויקט:** מינהל הגמ״ח | גרסה 4.5.0 | ללא נושא המעבר ל-SQLite
**תאריך:** 08/09/2026

**מטרת המסמך:** לרכז את ממצאי השיחה והסקירה של הקוד לנקודת עבודה אחת: מה דורש תיקון, מה כדאי לשפר, ומה צריך להפוך לתשתית לפני הוספת פיצ'רים נוספים.

**היקף:** המסמך עוסק באבטחה, אמינות נתונים ברמת האפליקציה, לוגיקה עסקית, UX, ארכיטקטורה, ביצועים, בדיקות, תחזוקה ותפעול. נושא המעבר למסד נתונים SQLite מפורט במסמך האפיון השני ([sqlite-migration-plan.md](./sqlite-migration-plan.md)) ונכלל כאן רק כאשר יש תלות שאינה ספציפית ל-DB.

---

## 1. עקרונות מנחים

- עדיפות ראשונה: אמינות של נתונים כספיים על פני מהירות הוספת פיצ'רים.
- כל פעולה פיננסית משמעותית צריכה להיות ניתנת לאימות, לשחזור, ולביקורת.
- לא לבצע שינוי רוחבי גדול ללא מנגנון rollback ובדיקות רגרסיה.
- להפריד בין UI, לוגיקה עסקית, שירותי יישום, ושכבת אחסון.
- להעדיף מנגנונים דטרמיניסטיים וברורים על פני "קסמים" והיוריסטיקות.

## 2. ממצאים קריטיים — עדיפות P0

| ממצא | חומרה | דרישה לתיקון |
|---|---|---|
| קוד מאסטר יומי נגזר מאלגוריתם קבוע בקוד המקור. מי שמכיר את הקוד יכול לשחזר אותו. | P0 — אבטחה | להחליף למנגנון שחזור/מנהל מאובטח שאינו ניתן לחישוב מה-client. |
| סיסמאות עוברות SHA-256 מהיר עם salt. זה עדיף על plaintext, אך אינו KDF ייעודי לסיסמאות. | P0 — אבטחה | לעבור ל-KDF מתאים כגון Argon2id / scrypt / PBKDF2 בהתאם ליכולות הסביבה. |
| `verifyPassword` משווה מחרוזות רגילות למרות הערה על timing-safe; אין השוואה constant-time אמיתית. | P0 — אבטחה | להשתמש בהשוואה constant-time במקום `===` כאשר יש מנגנון מתאים. |
| יש מסלול תאימות שמקבל סיסמה ישנה ב-plaintext ומבצע migration אוטומטי רק בעת ניסיון כניסה. | P0 — אבטחה | להגדיר מדיניות migration מפורשת, לתעד גרסת credential, ולוודא שאין plaintext שנשאר. |
| `db.run()` / `db.query()` הם שכבת SQL מדומה; פקודות לא מוכרות עלולות להחזיר תוצאה שנראית כהצלחה במקום להיכשל. | P0 — אמינות | עד המעבר ל-SQLite: fail-closed. כל פקודה לא מוכרת חייבת להחזיר שגיאה ולא `changes=1`. |
| שמירת נתונים היא fire-and-forget ברוב ה-call-sites; קיימת רק המתנה מפורשת באמצעות `flushPendingSave`. | P0 — אמינות | להגדיר מודל commit ברור לכל פעולה עסקית קריטית, ולוודא שהצלחה למשתמש משמעה שהשינוי הובטח. |

## 3. אמינות נתונים ולוגיקה עסקית — P1

| נושא | בעיה/סיכון | שיפור נדרש |
|---|---|---|
| Atomicity של פעולות | פעולה אחת יכולה לשנות כמה ישויות ברצף וליצור מצב חלקי במקרה כשל. | לרכז פעולות עסקיות ל-command אחד עם גבולות ברורים; עד המעבר ל-SQLite, ליצור rollback/compensation היכן שנדרש. |
| יתרות הלוואה | היתרה מחושבת בזמן קריאה באמצעות סריקת פירעונות. קיימת סכנה לפערים אם יש לוגיקה מקבילה במקום אחר. | להגדיר מקור אמת אחד לחישוב: `amount - סכום פירעונות תקפים`, עם invariant מרכזי. |
| מספרי הלוואות | נוסף `loan_number` בזמן `getAll`/`getById`, כלומר קריאה יכולה לשנות נתונים. | לא לבצע migrations/כתיבות בתוך read. להפריד migration ל-step מפורש. |
| Recurring | הקוד כולל הרבה תיקונים נקודתיים סביב סדרות, פירעונות, עריכה ויצירה אוטומטית. | להגדיר state machine וסכמת invariants אחת לכל משפחת recurring. |
| Soft delete | קיימות ישויות שבהן מחיקה היא soft-delete, ואחרות שבהן attachments נמחקים פיזית. | להגדיר מדיניות אחידה: מה ניתן לשחזר, מה נמחק פיזית, ומה קורה לילדים (child records). |
| Audit | אין שכבת audit מרכזית שמוכיחה מי שינה מה ומתי. | להוסיף Audit Log בלתי-תלוי ב-UI, כולל actor, entity, action, before/after, timestamp, וסיבה כשנדרשת. |
| Validation | חלק מהולידציות נמצאות בשירותים/טפסים ולא בהכרח בשכבת דומיין אחת. | לרכז invariants קריטיים בשירותי domain, ולהשתמש ב-schema validation לנתונים חיצוניים. |

## 4. באגים/סיכונים נקודתיים שנצפו

- ב-contacts קיים TODO להוספת תפקידים, ולכן יש פער בין היכולת המוצהרת של מודול אנשי הקשר לבין השלמות המימוש.
- `phoneValidation` מציין TODO לבדיקת donors/depositors כאשר יעברו ל-UUID; יש לוודא שהייחודיות והנרמול עקביים בכל הישויות.
- קיימת אי-אחידות בטיפוסי מזהים במספר מקומות: חלק מהקוד עבר ל-UUID string, בעוד טיפוסי contacts מסוימים עדיין מתעדים FK כמספרים. יש לבצע אחידות מלאה.
- יש שימוש נרחב מאוד ב-`any` בקוד המקור. הדבר מקטין את היכולת של TypeScript לתפוס שגיאות schema ושינויי מבנה.
- יש שימוש רב ב-`console.*`. חלקו שימושי לדיבוג, אך בסביבת production רצוי logger מרכזי עם רמות, context, ואפשרות לכבות/לשמור לוגים.
- יש `@ts-ignore` לפחות במקומות נקודתיים. יש להחליף בפתרון טיפוסים תקין או לעטוף API חיצוני ב-adapter.
- reset של שכבת ה-JSON מאפס localStorage אך אינו מייצג בהכרח reset של כל מקורות האחסון של סביבת desktop. זה עלול ליצור בדיקות/מצבי פיתוח מטעים אם משתמשים ב-reset כאילו הוא מוחק את כל ה-state.
- מנגנון fallback בין AppLocalData, AppData ו-localStorage מגדיל את מספר מצבי הקצה. גם בלי לשנות את ה-DB, יש להגדיר במפורש מקור אמת יחיד בכל runtime.

## 5. ארכיטקטורה ותחזוקתיות — P1/P2

- `App.tsx` מרכז bootstrap של שפה, protection, migrations, scheduler, auto-backup, ו-routing. מומלץ לפרק ל-`AppBootstrap`, `AppProviders` ו-`AppRouter`.
- `database.ts` הוא קובץ מרכזי מדי: הוא מכיל storage, מודל נתונים, repository-like services, וחישובים. יש להפריד שכבות גם אם נשארים זמנית עם JSON.
- להגדיר Repository interfaces לכל aggregate מרכזי: borrowers, loans, repayments, deposits, donations, guarantors.
- להימנע מקריאות ישירות ל-`getAllItems` מתוך קומפוננטות; כל גישה לנתונים צריכה לעבור דרך service/repository.
- להפחית כפילויות בין services באמצעות helper-ים דומייניים ברורים.
- להחליף `any` בטיפוסים ספציפיים בהדרגה, לפי מודולים בעלי סיכון גבוה.
- להגדיר Result/Error policy אחידה: מתי מחזירים Result ומתי זורקים exception. לא להשאיר שתי שיטות טיפול מעורבבות בלי כלל.

## 6. ביצועים — P1/P2

- ב-`getAll` של loans מתבצעת לולאה על כל ההלוואות, ובתוכה טעינת פירעונות לכל הלוואה. זה דפוס N+1 יקר ככל שכמות הנתונים גדלה.
- חישובי dashboard סורקים אוספים ומבצעים קריאות נוספות לכל deposit. יש להגדיר שכבת aggregation יעילה.
- חיפוש ב-JSON מבוסס על סריקות מערכים/אובייקטים. גם לפני SQLite כדאי לצמצם סריקות חוזרות ולבנות cache מחושב היכן שזה בטוח.
- Lazy loading של דפי React הוא כיוון טוב ויש לשמר אותו.

## 7. בדיקות — P1

הפרויקט כבר כולל תשתית משמעותית של Vitest, Testing Library, ו-fast-check, ולכן ההמלצה היא להרחיב את הקיים ולא להקים מערכת חדשה.

- להגדיר test fixtures יציבים ללווה/הלוואה/פירעונות/ערבים/הפקדות/תרומות.
- להוסיף invariants: יתרה לעולם אינה מחושבת באופן סותר; סכומי פירעונות אינם נעלמים; מחיקה אינה יוצרת רשומה פעילה; recurring אינו יוצר כפילויות.
- להרחיב property-based testing עם fast-check לתרחישים אקראיים של פירעונות, עריכות, מחיקות, ו-recurring.
- להוסיף בדיקות של כשלי persistence: כתיבה שנקטעת, JSON פגום, restore חלקי, backup ישן.
- להוסיף regression test לכל באג שמתוקן — לא רק תיקון בקוד.
- להריץ build + tests ב-CI לפני merge.

## 8. גיבוי ושחזור — P1

- להפריד בין "יצירת קובץ גיבוי" לבין "גיבוי מאומת".
- לאחר יצירת backup יש לבצע בדיקת parse/schema בסיסית ולשמור metadata.
- ב-restore: לבצע import לתוך staging, להריץ validation/integrity checks, ורק אז להחליף את מקור הנתונים.
- לשמור כמה נקודות גיבוי ולא רק קובץ אחרון כאשר המשתמש בוחר גיבוי אוטומטי.
- להוסיף מסך/דוח שמציג מתי בוצע backup אחרון והאם הוא עבר validation.

## 9. UX ותפעול — P2

- להימנע מהודעות כלליות כגון "אירעה שגיאה" בפעולות פיננסיות; להציג פעולה שנכשלה ומה ניתן לעשות.
- לפעולות מסוכנות: להציג preview של ההשפעה, במיוחד במחיקה, שינוי סדרת recurring, ושינוי סכומים.
- להוסיף undo/restore היכן שניתן, במיוחד לשינויים שאינם חייבים להיות בלתי-הפיכים.
- להציג מצב שמירה/שמירה שהושלמה רק כאשר יש ודאות שהפעולה נשמרה.
- לשמור על lazy loading והפרדה ברורה בין מסכי עבודה לכלים מתקדמים.

## 10. סדר עבודה מומלץ

1. **P0:** לסגור את חורי האבטחה ואת מנגנון ה-master code.
2. **P0:** לגרום לכל פעולה לא מוכרת בשכבת הנתונים להיכשל, ולא לדווח הצלחה מזויפת.
3. **P0/P1:** להגדיר commit semantics ופעולות עסקיות אטומיות ברמת service.
4. **P1:** להוסיף Audit Log ו-integrity checker.
5. **P1:** להוציא migrations מתוך read-paths.
6. **P1:** לייצב recurring ויתרות בעזרת invariants ובדיקות property-based.
7. **P1/P2:** להפריד App bootstrap ו-database/services לשכבות.
8. **P1/P2:** לשפר backup/restore ו-validation.
9. **P2:** ניקוי `any`, `console`, ו-`ts-ignore`.
10. **P2:** שיפורי UX וביצועים נוספים.
11. רק לאחר מכן: הרחבת פיצ'רים חדשים בקצב מבוקר.

## 11. Definition of Done לגרסת יציבות

- אין מסלול שבו פעולה לא מוכרת מדווחת כהצלחה.
- כל שינוי פיננסי קריטי ניתן לאיתור ב-Audit Log.
- כל ה-invariants של הלוואות ופירעונות מכוסים בבדיקות.
- אין migration שמתרחש כתופעת לוואי של read.
- Backup ניתן לאימות, ו-restore עובר validation לפני החלפה.
- build, tests, ו-CI עוברים באופן עקבי.
- המערכת מציגה למשתמש מצב שמירה אמין.
